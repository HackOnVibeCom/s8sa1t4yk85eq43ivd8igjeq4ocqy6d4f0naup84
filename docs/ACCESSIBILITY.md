# Accessibility approach

Accessibility is the product's subject and should also be a quality requirement for CANIGO itself. The application includes responsive layouts, visible labels and browser speech features, but the repository does not include a verified accessibility conformance report or user testing results.

## Current intent

- Present practical accessibility attributes instead of relying only on a generic venue label.
- Let community members add observations and evidence.
- Support responsive layouts and browser-based voice interaction where available.
- Keep evidence and AI outputs distinguishable from independently verified facts.

## What is not established

- WCAG conformance
- Screen-reader compatibility across supported browsers
- Complete keyboard-only operation
- Accuracy or recency of every venue attribute
- Reliability of microphone startup or speech recognition on a given device

## Before a judge demo or release

1. Test the primary path using keyboard only.
2. Verify visible focus and labels for form fields and icon-only controls.
3. Use a screen reader to test sign-in, venue details and contribution submission.
4. Test text resizing, contrast and mobile reflow on target devices.
5. Test voice only after explicit permission and confirm that a text path remains available.
6. Ask people with relevant lived experience to evaluate the journey; do not claim this evaluation has happened unless it has.
